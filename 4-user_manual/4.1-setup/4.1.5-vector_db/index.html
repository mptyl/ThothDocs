    Vector Database – Practical Guide

    This section provides a hands-on overview of the vector database in ThothAI. The goal is to explain, using non-technical language:

    • Why the vector database is necessary
    • How it is linked to the SQL database and to Workspaces
    • What it actually stores
    • What happens if it is not configured correctly

    1 - Why ThothAI needs a vector database

    ThothAI does not simply “translate” natural language questions into SQL. To answer intelligently it must understand the meaning of the sentences, recognize business concepts (not just column names) and reuse past experience.

    To achieve this it needs a semantic memory:

    • this memory is not the SQL database;
    • it is a vector database, where text and metadata are transformed into numerical vectors (embeddings) that can be searched by similarity.

    Practically speaking, the vector database allows ThothAI to:

    • recognize similar questions even if phrased differently;
    • link business expressions (e.g. “high-risk customers”, “recurring revenue”) to specific tables and columns;
    • reuse validated SQL queries when a new question resembles one already solved.

    If the vector database is missing or unreachable, ThothAI loses much of this contextual capability and some features may be unavailable.

    2 - How it connects to the SQL database

    In ThothAI every configured SQL database is associated with one dedicated vector database.

    Internally:

    • each SqlDb has a one-to-one link with a VectorDb object;
    • the VectorDb represents the collection / vector index containing the semantic context for that SQL database;
    • a Workspace relies on a single SqlDb and therefore also on its linked VectorDb.

    This means that:

    • every business database (e.g. a sales data mart) has its own vector collection;
    • all Evidence, Gold SQL and metadata related to that database are stored inside that collection;
    • when a user queries a Workspace, ThothAI uses only the vector DB associated with the Workspace’s SQL database.

    Keeping collections separate avoids mixing different contexts (e.g. HR vs. Sales data).

    3 - What the vector database contains

    The vector database mainly stores three categories of information:

    3.1 - Evidence (interpretation phrases)

    Evidence are short natural-language sentences that explain how to interpret specific business concepts relative to the data in the SQL database.

    They help to:

    • ensure ThothAI understands non-technical or ambiguous expressions;
    • link business wording to tables and columns;
    • document interpretation choices (e.g. the definition of “inactive customer” or “premium customer”).

    3.2 - Gold SQL (questions + validated queries)

    Gold SQL entries are real questions already solved, each composed of:

    • a natural-language question;
    • a validated SQL query proven to answer that question correctly.

    ThothAI can retrieve the Gold SQL entries most similar to the current question to:

    • improve the quality of newly generated SQL;
    • reduce logical errors;
    • keep answers aligned with established best practices.

    3.3 - Table and column metadata

    The vector database also stores metadata about tables and columns, such as:

    • textual descriptions (authored by analysts or generated via AI);
    • synonyms, tags, or business categories;
    • notes describing the meaning of values.

    These metadata allow ThothAI to:

    • understand the functional role of tables and columns;
    • bridge natural language and often cryptic technical names (e.g. clnt_actv_fl → “active client”);
    • guide users when navigating the schema.

    4 - What happens during preprocessing

    When you start preprocessing a Workspace (from the backend), ThothAI will:

    1. Read the schema of the SQL database linked to the Workspace.
    2. Build or update table and column descriptions (optionally leveraging AI).
    3. Send this information to the vector database, creating or updating the dedicated collection.

    If there are Evidence or Gold SQL entries (for example imported via CSV) they are saved in the vector database as well.

    During preprocessing the system:

    • expects the vector DB to be properly configured and reachable;
    • often clears the existing collection (to avoid duplicates) and rebuilds it with the new information;
    • logs any connection/configuration issue in the Workspace status and in the logs.

    If the vector DB is missing or misconfigured:

    • preprocessing can fail;
    • ThothAI will not be able to use Evidence, Gold SQL or metadata when generating queries.

    5 - Configuring the Vector DB (conceptual view)

    Actual configuration happens in ThothAI’s admin area (through backend models). Understanding what the main fields represent is usually enough for a non-technical reader.

    5.1 - Selecting a vector database engine

    ThothAI supports multiple vector-search engines, including:

    • Qdrant
    • ChromaDB
    • Milvus
    • PGVector

    In the standard Docker distribution, ThothAI ships with Qdrant preconfigured. Custom installations can point to external instances of any supported engine.

    For non-technical users it is enough to know that:

    • in a standard Docker install Qdrant is already provisioned;
    • switching to a different engine should only happen if corporate infrastructure requires it.

    5.2 - Collection name (Name)

    The name of the Vector DB corresponds to the collection (or index) where vectors are stored.

    Best practices:

    • choose a name that references the related SQL database (e.g. sales_dw, hr_reporting);
    • avoid generic names reused across environments to prevent confusion;
    • keep the one-to-one relationship between SQL databases and vector collections.

    5.3 - Connection parameters (host, port, path, URL)

    Depending on the engine, you will set parameters such as:

    • Host and Port (Qdrant, Milvus, PGVector);
    • Filesystem path (for some local ChromaDB configurations);
    • a full URL for managed cloud services.

    In standard Docker environments:

    • Qdrant already runs as an internal service;
    • default parameters usually work, unless the technical team decides otherwise.

    5.4 - Security and environments

    Additional fields (e.g. username, password, tenant, environment) are used to:

    • connect to cloud or multi-tenant services;
    • track the environment (development, staging, production).

    In many scenarios these fields are maintained by the technical team and require no action from business users.

    6 - Vector DB, embeddings and API keys

    The vector database always works together with an external embedding service that turns text into vectors.

    During installation the following are configured:

    • an embedding provider (e.g. OpenAI, Cohere, Mistral, HuggingFace, Anthropic);
    • a specific embedding model (e.g. multilingual model);
    • API keys to access the service.

    These parameters are managed through environment variables and typically handled by the technical team or installer.

    For non-technical users it is sufficient to remember that:

    • if embedding keys are not configured, the vector DB cannot work;
    • such errors surface during preprocessing or runtime (e.g. error messages in the backend or logs).

    7 - How to tell if the Vector DB is working

    When everything is configured correctly:

    • Workspace preprocessing runs successfully;
    • natural-language questions receive answers consistent with the business context;
    • the reuse of Evidence and Gold SQL is evident in the responses.

    If the vector database is misconfigured you may see:

    • explicit errors during preprocessing, indicating a missing or unlinked Vector DB;
    • messages reporting that the vector engine is unreachable;
    • behavior suggesting the system “ignores” metadata and examples, leading to less precise answers.

    In these cases contact the installation team (DevOps or system administrators) to check that:

    • the vector database service is running;
    • host, port and connection parameters are correct;
    • the embedding provider and API keys are properly configured.

    8 - Summary

    • The vector database is ThothAI’s semantic memory.
    • It is tightly linked to the SQL database: one vector collection per logical database.
    • It stores Evidence, Gold SQL and metadata that enrich the technical schema.
    • It is populated and refreshed during Workspace preprocessing and via optional CSV imports.
    • In the default Docker install ThothAI uses Qdrant, but other engines are supported.
    • A correctly configured Vector DB is essential to obtain high-quality answers to natural-language questions.
